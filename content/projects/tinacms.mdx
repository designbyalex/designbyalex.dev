  <mark>I led the UI/UX redesign of the TinaCMS v4 admin, end to end — from competitor research to a coded prototype and a Storybook design system that production is built from.</mark>

  TinaCMS was falling behind. Its rivals had moved on in feature parity, UX and cross-platform usability, and the new v4 admin shell had merged on a stock theme, <mark>with no reviewed design behind it.</mark> Editors couldn’t always tell whether their work was saved, which branch they were on, or why a save had failed.

  I worked as a design engineer, <mark>directing AI agents through every stage while making every design decision myself.</mark> In six weeks that covered 11 surfaces of the admin, each one designed in code, reviewed and handed to the TinaCMS developer to build.

    subheading: 13 rivals, 180+ screens, one verdict each
    headingSize: heading
    blocks:
      - _template: body
        body: |-
          I started by taking apart the competition. I reviewed 180+ screens from 13 content platforms, including Storyblok, Sanity, Payload, Statamic, Strapi, Sveltia and Decap, and gave every screen a verdict: steal, reference, avoid, or a gap nobody had filled yet. Alongside it, I audited the shipped v4 shell for branding and consistency.\
          \
          The research turned a vague brief into 11 design PBIs, one per surface of the admin. It also surfaced Tina’s clearest opening: none of the Git-based CMSs we compared showed the active branch while you edit and let you switch it in place.
      - _template: insights
        label: What the research showed
        items:
          - title: Navigation was the first argument
            text: Open issues disagreed on how the sidebar should work. I prototyped three mental models (Admin first, Site first and Changes first) and walked each one through the same four tasks. Admin first won.
          - title: Editors lost track of their work
            text: Saved or not, which branch, and whether a save was running or had failed were all shown differently, or not at all.
          - title: Branches were Tina’s edge
            text: Content lives in Git, so branches are native to Tina. No rival made them visible while editing, so that became the opportunity.

    heading: Editor state & saving
    subheading: Always knowing where you stand
    headingSize: statement
    blocks:
      - _template: body
        body: |-
          I designed a save model editors can read at a glance. The Save button shows saving, saved and failed states, with Retry when something goes wrong. The active branch shows in every view, and editors can switch it in place, save to a new branch, or discard and resume their unsaved work.\
          \
          v4 already got three things right: dirty dots on changed fields, unsaved badges in lists, and a prompt to resume unsaved edits. I kept all three and built the rest of the model around them.

  - _template: caseStudySection
    sectionId: errors
    heading: Errors
    subheading: From a blocked Save to a clear way forward
    headingSize: statement
    blocks:
      - _template: body
        body: |-
          A failed save used to leave editors guessing. I grounded the new pattern in primary research from GOV.UK, the NHS and the Government of Canada design systems. Errors appear only after a Save attempt, never while someone is still typing. A blocked Save becomes “Resolve errors”, which opens a summary pane listing every problem, and count chips on collapsed groups show where the hidden ones are.
      - _template: statement
        text: 'Every error is named, counted and one click away, '

  - _template: caseStudySection
    sectionId: media
    heading: Media
    subheading: No more losing an image without warning
    headingSize: statement
    blocks:
      - _template: body
        body: |-
          v4’s Media screen worked, but it had shipped without a design. Picking an image opened a large modal that hid the form and the preview. Delete asked “Are you sure?” without saying where the file was used. Uploads showed a single busy state for every file.\
          \
          I redesigned the library and its states, an upload card with progress for each file, delete that shows where a file is used, a picker that keeps the form in view, and the edge cases: permissions, protected branches and missing images. All of it works at desktop, tablet and phone widths, and I checked it against 60+ accessibility scenarios.
      - _template: statement
        text: 'Delete now shows where a file is used, '
        emphasis: so no page loses its image by surprise.

The prototype replaced the static Figma reference the epic had asked for, so the design that reviewers approved is the design developers build from.
